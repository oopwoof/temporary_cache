# 给编排方的调度说明

**你不判题。你只做调度、回收和格式核验。**

上一轮这个包在同一个会话里跑完三轮，结果 32 组分数**完全相同、零差异**——
三轮变成了一次判定复制三遍，噪声底测不出来，多数决也失去意义。
本轮的全部要求都是为了避免这一点。

**顺带的好处是快**：三轮本来就必须互相看不见，所以三轮天然可以同时跑。
串行等第一轮判完再开第二轮，既慢，又给你自己开了一条「上一轮是怎么判的」记忆通道。

## 一、你要做的

1. 打开 `调度清单.json`，里面的 `units` 就是要起的 subagent 清单
   （不分片时一个 unit = 一轮；分片时一个 unit = 一轮里的一片）。
2. **把全部 unit 一次性同时发起**，互相看不见。不要一个判完再起下一个。
3. 每个 unit 只给它自己那份材料：`dir` 指的那个 pass 目录、`cases` 列的那几题，
   外加 `judge_prompt.md`、`domain_pack.yaml`、`README.md`、`templates/ranking.json`。
   **不要把其他 pass 的任何内容给它。**
4. 每个 unit 独立判完自己那几题，把 `ranking.json` 写回 `pass<N>/case<NN>/ranking.json`。
5. 全部回来后，你做格式核验（见第三节），然后交回整包。

每个 unit 的任务书就是 `给每个subagent的prompt.md`，**逐字相同**，
只换 pass 号和题号清单——别的一个字都不要加，加了就不是同一个条件。

## 二、你**不能**做的（上一轮就是栽在这几条）

- ❌ **不要自己先读答复内容。** 你一旦形成判断，就会通过任务描述、追问、
  "参考一下"泄露给后续 subagent。你只需要知道目录结构，不需要知道里面写了什么。
- ❌ **不要跨 pass 比对，不要按文件哈希对齐三轮的洗牌映射。**
  甲乙丙丁在每轮是重新打乱的，这是设计，不是错误。
  你去把它们对齐，等于把一轮的判定复制到另外两轮。
- ❌ **不要把 pass1 的结果、倾向、"注意某某题有坑"之类的提示带给 pass2 / pass3。**
  同时发起就是为了让这件事没有机会发生；**不要为了"省事"改成串行**。
- ❌ **不要因为三轮结果不一致就去"统一口径"、"修正"、"复核后取一个"。**
  **三轮不一致正是本包要测的东西**——不一致的题数直接决定「最小可信胜场差」。
  一致率高是结果，不是目标。
- ❌ **不要自行改变分片。** 一轮内拆给几个 subagent 由出包方在出包前定死，
  写在 `调度清单.json` 的 `shards` 里。你自己再拆、或把几片并回一个会话，
  都等于换了一把尺子——而这批答复要和别的版本比。
  清单里怎么写就怎么起，觉得不合适就回来说一声，不要自己调。
- ❌ **同一题的四方不许拆开判。** 拆开就没有比较可言。

## 三、回收时只做这四项格式核验，不碰分数

1. **齐不齐**：`调度清单.json` 里每个 unit 的每一题都有 `ranking.json`，路径正确。
2. **字段全不全**：`case` / `ranking` / `scores` / `technical_failure` /
   `hard_gate_hits` / `why_first` / `why_last` 都有；`ranking` 覆盖该题全部标签且不重复；
   `scores` 的键与 `ranking` 一致。
3. **排序与分数自洽**：排序靠前的分不得低于排序靠后的（允许相等）。
4. **原句能对上**：`why_first` / `why_last` / `hard_gate_hits` 里的 `quote`
   要能在对应标签的答复原文里逐字找到，且 ≥10 字。

发现不合格的，**打回给那一轮的 subagent 重填，不要自己代填、代改**。
要打回多条时，**同样一次性全部发出去**，不要一条一条等。
若某个 subagent 反复给不出合格的 `quote`，如实记下来——这条会计入判分质量评估。

## 四、交回时附一句话说明

只需要说清四件事：

- 各 unit 是不是各自在独立 subagent 里完成的（是 / 否，否的话说明原因）
- 是**同时发起**还是串行跑的（应为"同时"）
- 有没有做过跨 pass 的比对或对齐（应为"没有"）
- 四项格式核验的结果，以及打回重填过几次

**不要在说明里汇总三轮的排序或分数，也不要评价一致性高低。**
那是调优侧解盲之后的事，你这边没有答案键，做不了也不该做。
