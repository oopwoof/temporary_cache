# 判分包说明｜runs/1/g0_pack（四方 × 8 题 × 3 轮）

## 一、先说三件会影响读数解释的事实

**1. 这一轮跑的是 v3.0，不是 v3.1。**
跑题方回执里校验通过的题包摘要是 `b5082cae…`，即我第一次给的那份；
后来因为覆盖核验补的 8 条（v3.1，摘要 `cbea92bb…`）没有进这次运行。
`SKILL.md` 指纹可对：他们跑的是 `f17f32c1…`，v3.1 是 `a2ef5d34…`。
**所以这批读数衡量的是 v3.0。** 不作废——v3.0 已含本轮全部主要改动；
v3.1 补的是执行层细节（报价时效、取整方向、币种含现金等），下一轮再测。

**2. 参评四方是 ours / base / WB / gpt，没有放 base+skill。**
不是漏了：判分方读的 `给每个subagent的prompt.md` 写死「四份答复（甲/乙/丙/丁）」，
而那几份文件明确要求不许改措辞（三轮独立靠它们守着）。放第五方会和这句冲突。
代价是 manifest 里 `hard: {no_loss_to: base+skill}` 这条**本轮无法在同一把尺子上核**，
记为**未测**。要核就另发一个成对包（`make_judge_pack.py`，阶段 4 专门做成对判定），
不要混进这一包。

**3. 跑题方自己的结论我复核过，不是照抄。**
- 16 份正文全部到齐，全文扫技术失败词（生成失败/请重试/已委派/后台执行中等）**零命中**；
- 交付件计数与他们回执一致（第 1 轮 24 件、第 2 轮 23 件），case05 两轮都是 0 件；
- 他们把 case07 的「已完成全部分析」判为误报——我回原文看了，那是面向用户的交付状态句，
  不是工具过程泄露，**同意误报**。但它确实没做到「首段直接写结论」，这算 v3.0 的一处未落地，
  会进 G2 复演报告，不影响判分。

## 二、包里有什么 / 怎么发

```
runs/1/g0_pack/
├── pass1|2|3/case01..08/题面.md + 题面附件/ + 答复/{甲,乙,丙,丁}.md(+_交付文件/)
├── judge_prompt.md              判定顺序、扣分引原句要求
├── domain_pack.yaml             领域口径（已脱敏：出处标注与方别名都不在里面）
├── 给编排方的调度说明.md  ← 措辞不要改
├── 给每个subagent的prompt.md ← 措辞不要改
├── 调度清单.json                3 个 unit，一次性同时发起
└── README.md
```

**三轮必须由互不可见的会话完成，一次性同时发起**，不要判完一轮再开下一轮。
每轮的甲乙丙丁是重新打乱的（同一题三轮的映射都不同，我抽查过），这是设计。
答案键在 `runs/1/_answer_key/g0_keys.json`，**留在我们这边，不随包外发**。

## 三、无平信号：这一包本身就带，不用额外要

之前提的「8 个 skill 全卡在 ≥6/8 超过、根因是 29% 平局率」——这一包的设计已经把它解决了：

- `judge_prompt.md` 要求**从好到差的完整排序**（严格序，不允许并列）→ 这就是无平信号；
- 同时要 **1-5 分**绝对打分（允许同分）→ 这是分差信号。

`gates/thresholds.yaml` 里 `winrate_tie_mode: rank` 已经设成「分数打平时看名次」，
两个信号都会被用上。**不需要再向判分方追加要求**，照包里的措辞发即可。

## 四、外发前自查：1 处误报，已放行

打包脚本报了 3 处「专家信息」泄露，全是同一句、同一个词：

> case07 题面第 87 行：`action_priority.csv`：逐标的减仓/退出排序、证据、可执行状态、现金贡献、风险改善和**排序理由**

命中的是 `排序理由` 这个词。回原文核实：它是**题面自带**的 CSV 列名要求（原始题包里就有，且只出现这一次），
不是专家备注或评分材料。**判为误报，放行，不改题面**——改题面等于改题。

其余无命中：答复正文里没有评分、问题标签、槽位身份的残留（我逐份扫过）。

## 五、脱敏与残余风险

见 `runs/1/judge_inputs/脱敏日志.md`。一句话：对五方一律执行同一条规则——
正文里的产品/系统身份标识（workbuddy、doubao 等）替换为「系统」，只动标识本身，
路径结构与决策内容一字未改。实际命中 5 处，都在同一方的输出目录路径里。

**残余风险如实记录**：交付文件名里的 `JZ-test-portfolio-trading-decision-NN` 前缀，
base、WB 两方在用，ours 与 gpt 不用。它不指向具体某一方，但会把四方聚成两簇。
我没有改名，因为正文里有对文件名的引用，改名会引入新的不一致。
判分回来做质量核查时应一并看这条。

## 六、回来之后按这个顺序算（不要跳步）

```bash
# 1. 先跑质量核查，退出码 2 的读数不许进准出核算
python3 <autotune>/scripts/check_judge_quality.py --pack runs/1/g0_pack \
    --keys runs/1/_answer_key/g0_keys.json --out runs/1/判分质量.md

# 2. 再算准出。--per-pass 必须给，不给就是先平均再核，会把达标的那一轮抹平
python3 <autotune>/scripts/score_release.py --run runs/1 \
    --thresholds gates/thresholds.yaml --candidate ours --per-pass \
    --out runs/1/准出核算.md
```

质量核查要重点看三件事：三轮是不是真独立（直接比 pass1/2/3 的分）、
分数分布有没有塌到两端、`hard_gate_hits` 字段用了几次（**全程 0 次是异常信号，不是没问题**）。

## 七、准出判据（回来之后对照这个看）

| 对手 | 条件 | 说明 |
|---|---|---|
| 对 base（裸模） | 均分差 ≥0.4 **且** 胜率 >60% **且** 8 题至少 6 题**严格超过** | 三条全过 |
| 对 WB | 胜率 >60%；**或** 对裸模分差 >0.5 且对 WB 胜率 ≥50% | 二选一 |

两条路径须在**同一轮内同时**满足；三轮里**任一轮满足即可**。
gpt 参与比较但不进判据。**胜率必须同时报口径**（平算半 / 不计平 / 胜总），不标口径的胜率作废。

起点提醒：上一轮 v1.0 的读数是对裸模分差 **−0.75**、超过题数 **1/8**、对 WB 胜率 62%。
要达标，分差要从 −0.75 抬到 +0.4 以上，**净变化 ≥1.15 分**。
